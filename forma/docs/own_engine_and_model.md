# Свой движок, управляемый нейросетью, и своя нейросеть: что реально, а что нет

Ответ на три вопроса подряд: можно ли сделать «свой Unity» с управлением
через нейросеть, в чём суть движка и хватит ли этого на свою игру; можно ли
создать свою нейросеть и заставить GitHub считать за вас.

Все числа — проверяемые: размеры кода взяты из GitHub languages API, лимиты —
из документации GitHub, скорость обучения — замером в этом же сандбоксе.
Скрипт бюджета: `docs/train_budget.py`. Схемы: `docs/img/engine_layers.svg`,
`docs/img/nn_where.svg` (`docs/make_engine_svg.py --check`).

---

## 0. Шесть ответов сразу

1. **«Свой движок, управляемый нейросетью» — да, но это не «свой Unity».**
   Это слой поверх готового рантайма: DSL + проверки + рендер картинки назад
   модели. Форма уже ровно это и делает для геометрии. Менеджер сцены, физику
   и рендер писать не надо.
2. **С нуля — нет.** Полный движок — 0,5–2,1 млн строк. У ФОРМЫ сейчас
   44,5 тыс. строк Python, и это один слой из двенадцати.
3. **Игру — да.** Не «свою GTA», а игру на 1–10 часов контента: 3D-пазл,
   песочница, тактическая головоломка. Узкое место — не движок, а контент и
   отладка.
4. **Свою нейросеть — да**, если это специалист на 1–20 млн параметров,
   обученный на данных, которые генерирует ваше же ядро. Универсальную модель
   «фото → 3D» — нет: там 10³–10⁵ GPU-часов и датасеты в миллионы объектов.
5. **GitHub как вычислитель — частично.** 4 ядра, 16 ГБ, 14 ГБ диска, 6 часов
   на job, GPU нет; для публичных репозиториев бесплатно. Но по правилам
   GitHub Actions нельзя использовать как «серверное окружение» для чужих
   задач — только производство, тестирование, развёртывание и публикация
   проекта этого репозитория. Обучение модели для этого же проекта — можно;
   «крутить нейросеть вместо своего ноутбука круглосуточно» — нет.
6. **Мощность, которая влезает:** 1,7–4,4 млн параметров обучаются за 1–2
   job'а по 6 часов; 17 млн — это уже недели на CPU. Запуск — 17 МБ весов и
   45 мс на кадр на обычном ноутбуке. Для вашей задачи (силуэты, формы,
   геометрия) этого достаточно, если не пытаться заменить этим TripoSR.

## 1. Что такое движок на самом деле

Схема: `docs/img/engine_layers.svg`.

Движок — это не «место, где расставляют фигурки». Это двенадцать слоёв, и
каждый существует потому, что без него игра не работает:

| Слой | Работа | Объём, строк | У ФОРМЫ |
|---|---|---:|---|
| 1. Рантайм и память | запуск сцены, сборка мусора, горячая перезагрузка | 10⁴–10⁵ | нет |
| 2. Сериализация сцены | сцены и префабы как файлы, ссылки на ассеты | 10⁴ | нет (есть DSL-сценарий) |
| 3. Рендерер | конвейеры, шейдеры, тени, постобработка | 10⁵–10⁶ | чужой: three.js |
| 4. Физика | столкновения, твёрдые тела, шарниры, ткань | 10⁵ | чужой, не подключён |
| 5. Анимация | скелет, морфы, стейт-машины, кривые | 10⁴–10⁵ | часть: `animate`, `keys` |
| 6. Импорт ассетов | FBX/GLB/PNG/звук → внутренний формат, GUID | 10⁴ | часть: GLB, OBJ, STL, PLY |
| 7. Звук | микшер, 3D-панорама, события | 10⁴ | нет |
| 8. Ввод и UI | клавиши, геймпад, канвас, раскладка | 10⁴ | нет |
| 9. Навигация и ИИ | сетка проходимости, поиск пути, поведение | 10⁴ | нет |
| 10. Редактор | инспектор, гизмо, undo, режим Play | 10⁵ | свой, но простой |
| 11. Сборка под платформы | Windows, Web, Android, консоли | 10⁴–10⁵ | Web (GLB), exe |
| 12. Сеть и сервисы | мультиплеер, аккаунты, магазин | 10⁴ | нет |

Размеры для сравнения (GitHub languages API, байты кода):

| Проект | Код | Оценка строк |
|---|---:|---:|
| Godot | 73,6 МБ C++ и др. | ≈2,1 млн |
| Babylon.js | 50,1 МБ | ≈1,4 млн |
| Bevy (ядро) | 22,6 МБ Rust | ≈0,65 млн |
| three.js | 17,4 МБ JS | ≈0,5 млн |
| ФОРМА | ≈1,6 МБ Python | 44,5 тыс. |

**Почему суть вашего вопроса верна и одновременно опасна.** Верна: игра — это
действительно «фигурки + логика + анимации + кнопки». Опасна: 90 % работы в
движке — не фигурки, а то, что вокруг: загрузка ассетов, дрожание кадра,
сохранения, столкновения, звук, сборка под платформы, и главное — **отладка**.
Нейросеть отлично пишет код, но не отлаживает за вас игру на 10 часов,
потому что для этого нужен цикл «запустил → увидел → поправил», который
сейчас делают MCP-серверы (см. §3), а не одна генерация.

## 2. «Движок, управляемый нейросетью»: что это на самом деле

Тут смешаны две разные вещи, и их надо разделить, иначе проект утонет.

### 2.1 Нейросеть **внутри** движка (в рантайме)

Модель работает в момент игры: распознаёт, что нарисовал игрок, генерирует
уровень, управляет персонажем, озвучивает реплики.

| Что можно | Цена | Годится ли на ноутбуке |
|---|---|---|
| Классификатор/сегментация 1–20 M, ONNX на CPU | 5–80 МБ, 10–60 мс | да |
| Небольшой генератор текста (1–3 B, квантованный) | 0,5–2 ГБ, 1–5 с/ответ | да, но медленно |
| Генерация 3D-модели по тексту в рантайме | сотни миллионов параметров и больше | нет: секунды-минуты, гигабайты |
| Управление анимацией/мимикой по камере | 5–50 M | да (MediaPipe-класс) |

### 2.2 Нейросеть **над** движком (в редакторе) — и это уже продукт

Модель не внутри игры, а за пультом: пишет сцену, скрипты, запускает проект,
читает ошибки, делает скриншот и правит. Именно это вы и имеете в виду под
«управляемый через нейросеть», и это уже работает у других:

| Инструмент | Что делает | Факт |
|---|---|---|
| Godot-MCP (Asset Library) | 24 инструмента: узлы, ресурсы, скрипты, скриншоты, консоль, ошибки рантайма | опубликован 31.10.2026, Apache-2.0 |
| Godot MCP Pro | 169 инструментов, WebSocket к редактору, undo/redo, ввод в запущенной игре | 295 звёзд, платный ($5) |
| GDAI MCP | плагин в редакторе Godot 4.2+: сцены, узлы, скриншоты, ввод | $19 |
| Unity-MCP (аналог) | то же для Unity | упоминается как «counterpart» в описании Godot-MCP |

Вывод: **никто не пишет свой движок ради управления нейросетью.** Пишут MCP-
сервер к существующему. Это в 100–1000 раз дешевле и сразу даёт физику,
звук, UI, сборку под платформы.

### 2.3 Почему DSL ФОРМЫ — правильный выбор именно для нейросети

Ваш вопрос «можно ли управлять движком через нейросеть как ФОРМУ» имеет
технический ответ: **да, и текстовый DSL лучше визуального редактора.**
Причины, все проверяемые:

1. **Цена контекста.** Одна команда ФОРМЫ — 343 знака в справке (≈107
   токенов), весь каталог 227 команд — ≈83 тыс. токенов. Сцена на 100 команд —
   ≈10 тыс. токенов. Для сравнения: сцена Godot в `.tscn` — XML на десятки
   тысяч строк, а скриншот редактора — картинка, по которой модель не считает
   геометрию.
2. **Проверяемость.** У ФОРМЫ 25 правил проверки и метрики (объём, род,
   зазоры, стенка, наклон). Модель может выдать 20 вариантов, и 19 отсеет
   машина, а не человек.
3. **Детерминизм.** Один и тот же сценарий даёт один и тот же результат —
   значит возможен автооткат и A/B-сравнение.
4. **Обратная связь.** Ошибка ФОРМЫ — это `message` + `hint` + строка, то
   есть текст, который модель понимает. Ошибка в игре — это «персонаж
   провалился», и её надо ещё поймать.

Именно поэтому рецепт «свой движок» на практике выглядит так: **свой DSL и
свои проверки, чужой рантайм**. У ФОРМЫ уже есть первая половина; вторая —
three.js для показа.

## 3. Можно ли сделать «свой Unity»: три честных варианта

| Вариант | Что писать | Объём | Срок в одиночку | Когда имеет смысл |
|---|---|---:|---|---|
| **A. Слой поверх готового рантайма** (Godot/three.js/Bevy + MCP + свой DSL) | DSL, проверки, MCP-обвязка, шаблоны игр | 5–20 тыс. строк | 2–4 месяца до первой играбельной сцены | всегда, если цель — игра |
| **B. Свой формат и редактор, чужой рантайм** (как ФОРМА + three.js) | редактор, сериализация, экспорт GLB, игровой слой | 20–60 тыс. строк | 6–12 месяцев | если нужен свой язык описания (геометрия, чертежи, обучение) |
| **C. С нуля** | всё двенадцать слоёв | 0,5–2 млн строк | 5–15 лет командой | только если это и есть продукт (как Godot) |

Цифры варианта A не выдуманы: 24–169 инструментов у существующих MCP-серверов
— это и есть весь «слой управления». Ваш собственный вклад — не движок, а
**предметная область**: у ФОРМЫ это геометрия и проверки, которых нет ни в
Godot, ни в Unity.

### 3.1 Что это значит для вашей игры

Минимальная играбельная 3D-игра на таком слое:

1. **Сцена**: 10–30 объектов, каждый — команда DSL (или импорт GLB из ФОРМЫ).
2. **Игрок**: капсула + камера + ввод. Ввод — единственное, чего у ФОРМЫ нет
   вообще.
3. **Правила**: подобрал/поставил/соединил — 100–300 строк логики.
4. **Состояние**: сохранение сцены в файл (у ФОРМЫ сценарий уже
   сериализуется текстом — это плюс).
5. **Обратная связь**: звук, подсветка, анимация. Звука нет — это
   единственный слой, который придётся взять готовым (Web Audio).

Итого: **игру сделать можно, но не «своим движком», а своим DSL поверх
чужого рантайма.** Если попытаться писать движок, через полгода будет
полуфабрикат без игры; это самый частый способ не сделать игру.

### 3.2 Где нейросеть помогает, а где мешает

| Этап | Помогает | Мешает |
|---|---|---|
| Идея и правила | да, сильно | придумывает неиграбельное, надо играть самому |
| Контент (модели, тексты, звук) | да, если есть пайплайн и проверки | «сгенерируй 100 уровней» → 95 неиграбельны |
| Код логики | да, 100–300 строк за раз | не видит, что игра «невесёлая» |
| Баланс и ощущение | почти нет | нужен человек с геймпадом |
| Отладка | только с MCP (модель должна видеть ошибки и кадр) | без обратной связи выдумывает причины |

## 4. Своя нейросеть: в чём суть

Нейросеть — это функция с числами-настройками (весами). «Обучить» = подобрать
числа так, чтобы на ваших примерах ответ совпадал с правильным. Число весов и
есть «размер» модели: 1,7 M параметров ≈ 7 МБ в fp32 или 1,7 МБ в int8.

Три способа «создать свою», по возрастанию цены:

| Способ | Что делаете | Данных нужно | Время | Результат |
|---|---|---|---|---|
| **1. Взять готовую и настроить** | ONNX-модель + своя логика поверх | 0 | часы | работает сразу, но «как у всех» |
| **2. Дообучить готовую** | берёте энкодер (MobileNet/ResNet) и учите свою голову | 1–20 тыс. примеров | часы–дни на CPU | ваша задача решается хорошо |
| **3. Обучить с нуля** | своя архитектура и все веса | 50 тыс. – миллионы | недели–месяцы на CPU | нужно, только если данные уникальны |

Для вашей задачи правильный ответ — **2**: чужие глаза (энкодер), свои мозги
(голова), и **свои данные из своего ядра**.

### 4.1 Три вида задач, которые вам нужны

| Задача | Вход | Выход | Размер | Где взять данные |
|---|---|---|---|---|
| **Восприятие силуэта** | маска 96×96 | 20–40 чисел: габарит, наклон, число деталей, род | 0,1–1 M | генерирует ядро: случайная сцена → рендер маски |
| **Форма из фото** | RGB 96×96 / маска | SDF 32³ или 20 параметров DSL | 1,7–4,4 M | пары «фото ↔ форма»: рендер своей же модели + фото из сети |
| **Критика и проверка** | форма (SDF/параметры) + фото | «похоже / нет» + где расходится | 0,5–2 M | сравнение через `deviation` и `iou` — уже есть в `forma/vision/` |

Ключевая идея, которая делает всё это возможным **без чужих датасетов**:
ваше ядро само производит бесконечные правильные примеры. Случайная сцена →
рендер с 4 ракурсов → маска и глубина (это «вход») → исходные параметры и SDF
(это «ответ»). Метки точные по построению, а не размеченные руками. Такой
цикл называется самосогласованным (self-supervised) и он единственный, который
реально поставить в одиночку.

## 5. GitHub как вычислитель: что можно, что нельзя, сколько даст

Схема: `docs/img/nn_where.svg`.

### 5.1 Железо и лимиты (документация GitHub, 2026)

| Параметр | Публичный репозиторий | Приватный (план Free) |
|---|---|---|
| Ядра / RAM | 4 / 16 ГБ (`ubuntu-latest`) | 2 / 8 ГБ |
| Диск | 14 ГБ SSD | 14 ГБ |
| GPU | **нет** | нет |
| Время одного job | 6 часов | 6 часов |
| Одновременных job | 20 | 20 |
| Цена | бесплатно и без лимита минут | входит $12 вычислительного бюджета в месяц, дальше $0,006/мин |
| Кэш | 10 ГБ на репозиторий | 10 ГБ |
| Артефакты | 500 МБ | 500 МБ |
| GPU-раннеры больших размеров | до 100 одновременных | только Team/Enterprise, платно |

Кэш живёт между запусками, но если его не трогали 7 дней — GitHub его
удаляет. Значит чекпойнт модели надо сохранять **артефактом или в релиз**, а
не только в кэш.

### 5.2 Правила, а не только лимиты

Цитата из GitHub Terms for Additional Products and Features (раздел Actions,
редакция от 27.08.2026): Actions не должны использоваться для

> …любой другой деятельности, не связанной с производством, тестированием,
> развёртыванием или публикацией программного проекта, связанного с
> репозиторием, где используются GitHub Actions.

Плюс отдельно запрещены криптомайнинг, создание нагрузки, «несоразмерной
пользе», и предоставление Actions как сервиса для третьих лиц.

Практический перевод:

| Хочу | Можно? |
|---|---|
| Учить свою модель для этого проекта, чекпойнты в релиз | **да** |
| Гонять тесты, сборку, генерацию документации и схем | **да** |
| Держать «сервер» с моделью, к которому обращается игра | **нет** (serverless-нагрузка) |
| Круглосуточно считать что-то, что не относится к репозиторию | **нет** |
| Отдать репозиторий другим, чтобы они «крутили» вашу модель | **нет** |

Формулировка «жрать не мои ресурсы, а гитхабовские» в буквальном виде — это и
есть нарушение: Actions — не бесплатный облачный сервер для ваших задач, а
CI для проекта. Отличие не юридическое, а смысловое: обучение модели, которая
лежит в этом же репозитории и нужна его продукту, — часть проекта.

### 5.3 Альтернативы, если нужен GPU

| Вариант | Что даёт | Цена | Ограничение |
|---|---|---|---|
| Аренда GPU (RunPod, Vast, Lambda) | T4/A10 на часы | 10–40 ₽/ч | оплата за рубежом, настройка |
| Google Colab / Kaggle | T4/P100 бесплатно с лимитом сессий | 0 | сессии обрываются, нельзя в CI |
| Hugging Face Spaces/Jobs | сборка и запуск демо | от 0 | публичность, лимиты |
| Свой ноутбук | без интернета и лимитов | 0 | 2 ядра → дни вместо часов |

Честно: **для вашей задачи GPU не обязателен.** Модель на 1,7 M параметров
учится на 4 ядрах за ~7 часов — это один job и одна ночь. GPU нужен, если
захочется 20 M+ или диффузию.

## 6. Насколько мощная сеть влезает: арифметика

Скрипт: `python docs/train_budget.py`.

Как считается. Для свёрточной сети прямой проход складывается из свёрток
3×3: `2 · 9 · C_in · C_out · R²`. Обучение втрое дороже. Скорость железа —
измеренная, а не паспортная: numpy im2col-GEMM на 2 ядрах этого сандбокса дал
**150 GFLOP/s** (матрица 1024², fp32), PyTorch на обвязку съедает примерно
столько же, поэтому в расчёте КПД 50 %.

| Задача | Параметров | Вход | Сэмплов × эпох | 4 ядра | GPU | В 6-часовой job |
|---|---:|---|---:|---:|---:|---|
| Голова: силуэт → 20 чисел формы | 0,1 M | 96² | 20 000 × 30 | 39 мин | 10 мин | влезает |
| UNet 24: силуэт → SDF 32³ | 4,4 M | 96² | 50 000 × 20 | 12,7 ч | 3,2 ч | нет, 2 job'а |
| UNet 48: маска → глубина | 17,7 M | 128² | 50 000 × 20 | 3,8 сут | 22,6 ч | нет, 15 job'ов |
| UNet 96: кромки и фаски | 70,7 M | 192² | 20 000 × 10 | 6,8 сут | 40,8 ч | нет, 27 job'ов |
| TripoSR-класс (для сравнения) | сотни млн–1 млрд | 256² | 100 000 × 10 | — | тысячи часов | нет |

Сколько сэмплов проходит за один 6-часовой job (4 ядра, КПД 50 %):

* голова 0,1 M при 96² — **5,5 млн**;
* UNet 24 (4,4 M) при 96² — **471 тыс.**;
* UNet 48 (17,7 M) при 128² — **66 тыс.**

Отсюда рабочая вилка: **1,7–4,4 M параметров** — то, что обучается за один-два
job'а; 17 M — на грани; 70 M и больше — только с GPU. И это оценка снизу: на
практике PyTorch на CPU даёт 30–60 % от этого, а данные и препроцессинг
съедают ещё столько же времени, сколько сам расчёт.

Важная оговорка про формулу «2 · N · R²»: она годится для сетей с плотным
предсказанием (маска, глубина, SDF) и врёт для классификаторов: у ResNet-50
тяжёлые слои стоят на разрешении 7×7, поэтому паспортные 4,1 GFLOP против
2,5 TFLOP по этой формуле — в 600 раз. Поэтому в скрипте калибровка по слоям,
а не по числу параметров.

## 7. Ваша задача: силуэты, формы, геометрия

Три головы, которые вместе дают «восприятие формы», и каждая по отдельности
полезна.

### 7.1 Голова «силуэт → параметры» (0,1–1 M)

Вход: маска объекта 96×96 (её уже умеет `forma/vision/silhouette.py`).
Выход: 20–40 чисел — габарит, положение центра, наклон главной оси, число
выступающих деталей, «дырки», примерный род.

Обучение: ядро генерирует случайную сцену → рендер маски → ответ известен.
За один 6-часовой job проходит 5,5 млн примеров — то есть датасет можно
сделать за одну ночь и не хранить.

Зачем: это «быстрый взгляд» — за 10 мс сказать, с чем вообще имеем дело, до
запуска тяжёлой реконструкции.

### 7.2 Голова «фото → форма» (4,4 M, UNet 24)

Вход: маска + 4 ракурса (или одна маска и глубина от готовой модели).
Выход: SDF 32³ — грубая форма, которую ядро дальше доводит до точной
геометрии подгонкой параметров.

Почему SDF, а не меш: SDF — непрерывное поле, из него `from_sdf` в ядре уже
строит тело; ошибка сети становится «мягкой» и лечится подгонкой, а не даёт
дырявый меш.

Почему 32³, а не 128³: 32³ = 32 тыс. чисел, ошибка головы 4,4 M на таком
выходе ещё обучаема; 128³ — это 2 млн чисел, для них нужна модель на 50 M+.

### 7.3 Голова «критика» (0,5–2 M)

Вход: форма (SDF или параметры) + фото. Выход: скаляр «похоже» и карта
расхождений.

Тут есть готовый учитель: `forma/vision/fit.py` и `iou`, `deviation` дают
число без нейросети. Значит голову можно учить на **разнице между рендером
модели и фото** — а это и есть настоящая цель, а не «угадать форму».

### 7.4 Что брать готовым и не учить

| Готовое | Зачем | Почему не учить |
|---|---|---|
| Depth Anything V2 | глубина по одному фото | по карточке модели от 25 M (ViT-S) до 1,3 B (ViT-G); обучено на миллионах изображений |
| SAM / SAM2 | маска объекта | сегментация — решённая задача, ваши данные её не улучшат |
| TripoSR / InstantMesh | черновая 3D-форма | сотни миллионов–миллиард параметров, тысячи GPU-часов |
| MediaPipe | поза/лицо, если нужна анимация | отлажено, работает на телефоне |

Правильная схема: **готовая модель даёт черновик, ваша маленькая голова
переводит черновик в ваш DSL, ваше ядро доводит до точной геометрии и
проверяет.** Так вы получаете свою нейросеть там, где она действительно ваша
(форма → параметры вашего языка), и не платите за то, что уже сделано.

### 7.5 План на 6 недель с воротами

| Неделя | Что | Ворота (проверяемое число) |
|---|---|---|
| 1 | Генератор данных: 10 тыс. сцен → маска 96² + SDF 32³ + параметры | датасет строится за < 30 мин, метки совпадают с `build()` |
| 2 | Голова «силуэт → габарит и наклон» (0,1 M), обучение в одном job | ошибка габарита < 5 %, наклон < 3° |
| 3 | UNet 24 «силуэт → SDF 32³», обучение в 2 job'а с чекпойнтом | IoU маски > 0,9; SDF → тело через `from_sdf` без дырок |
| 4 | Подгонка: SDF → параметры DSL (`fit.py` + оптимизация) | `deviation` < 1 мм на 80 % тестовых сцен |
| 5 | Критика: голова «похоже/нет» против `iou` | согласие с `iou` > 90 % |
| 6 | Обёртка: `форма.vision.estimate(фото)` → сценарий DSL | одна команда, время < 2 с, ONNX 17 МБ |

Каждая неделя заканчивается **числом**, а не «выглядит неплохо». Это то же
правило, что уже работает в документах по топологии и по фото.

### 7.6 Три способа провалить этот проект

1. **Начать с «сделаю свой Unity»** — через полгода нет ни игры, ни сети.
2. **Начать с «обучу модель понимать 3D»** — на 4 ядрах это займёт годы;
   начинать надо с головы на 0,1 M на своих данных.
3. **Собирать датасет руками** — 10 тыс. масок разметить вручную невозможно;
   их должно рисовать ваше же ядро.

## 8. Что в итоге делать

**Движок.** Не писать. Взять three.js (уже есть в проекте) + физику (Jolt или
Rapier) + звук (Web Audio), а своим оставить DSL, проверки и предметную
геометрию — то, чего нет ни у кого. Управление нейросетью — через MCP-сервер
к своему же DSL: инструменты = команды, обратная связь = ошибки и скриншот.

**Игра.** Делать маленькую: 10–30 объектов, 100–300 строк логики, 1–3 часа
контента. Сценарий ФОРМЫ уже сериализуется текстом — это готовая система
сохранений и «уровней».

**Нейросеть.** Своя — на 1,7–4,4 M параметров, три головы (силуэт → числа,
силуэт → SDF, критика), данные из своего ядра, чужие модели только как
черновик. Обучение — в 1–3 job'а на GitHub (это законно, потому что модель
часть проекта) или ночь на ноутбуке; запуск — ONNX на 17 МБ, 45 мс на кадр.

**GitHub.** Не как сервер. Как CI, где модель собирается, тестируется и
публикуется релизом; чекпойнты — артефактами. Для круглосуточного инференса —
свой ноутбук или браузер игрока (WASM).
