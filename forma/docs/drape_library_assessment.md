# Драпировка: оценка готовых библиотек для самостоятельной Формы

**Вывод этапа:** основной кандидат — IPC Toolkit для непрерывного обнаружения
и геометрии контакта. Существующий решатель Формы пока остаётся ответственным
за движение, длины, изгиб, толщину и мягкие тела. Это решение о направлении,
а не готовая интеграция: итоговый `drape` и Windows EXE всё ещё не исправлены.
Blender не используется и не планируется как зависимость.

## Проверка IPC на двух настоящих ошибочных шагах

Предыдущий шестисценный опыт не доказывал, что IPC-поправки реально нужны:
они ни разу не сработали после других экспериментальных поправок. Поэтому
мы взяли **неизменённый штатный решатель** и остановили его на первом шаге,
который CCD посчитала небезопасным. Затем применили к этому одному переходу
наш пробный корректор, использующий IPC. Проверка выполнена на Linux,
Python 3.11.2, IPC Toolkit 1.6.1; исходные `.forma` не менялись.

| Переход | Лист на шаре | Рукав вокруг капсулы |
|---|---:|---:|
| Первый небезопасный шаг | 2 | 36 |
| FCL: пары с опорами до → после | 6 → 0 | 110 → 0 |
| CCD до → после | небезопасен → безопасен | небезопасен → безопасен |
| Локальные события / общие откаты | 1 / 0 | 22 / 1 |
| Изменённых вершин при коррекции | 4 из 448 | 768 из 768 |
| Наибольшее изменение ребра до → после | приблизительно 0 → 0,038% | 0,492 → 1,196% |
| Нормальная проекция найденных пар после | 99,982–100,000% | 99,871–100,025% |
| Время самой пробной поправки, с | 0,52 | 0,95 |

FCL учитывает *касание или пересечение*, не различая их; здесь она проверяла
только конец перехода тела относительно суммарной опоры. CCD проверяет
линейный отрезок после предварительного размещения, исключает соседние
примитивы и использует тот же IPC Toolkit, что и пробный корректор, то есть
это не независимая библиотека. Число локальных событий может включать повторные
рассмотрения одной пары. Нормальные проекции оценивают лишь найденные пары
стенки, а не всю толщину; жёстко закреплённых точек в этих двух сценах нет.
У рукава после локальных попыток был применён общий откат, поэтому изменились
все 768 вершин. Малое движение после такого отката **не доказывает равновесия**.

**Значение:** IPC вместе с нашим адаптером показал полезность на реальных
проблемных переходах, а не только на синтетическом примере. Но мы исправили
лишь **по одному шагу**: симуляция после него не продолжалась. Это не
доказывает, что ткань правильно ляжет, что сохранены все длины/толщины или что
скатерть свесится. В предыдущем полном шестисценном опыте изменение ребра
рукава вокруг капсулы доходило до 21,58%, а скатерть не свисала как нужно:
[прошлый отчёт](drape_ipc_short_status.md). Результаты двух отдельных шагов
и версии исходников:
[`ipc-first-impact-ball.json`](../benchmarks/drape_six/ipc-first-impact-ball.json),
[`ipc-first-impact-rod.json`](../benchmarks/drape_six/ipc-first-impact-rod.json).
Время измерено в исследовательском Python на одном Linux-окружении; скорость
готового EXE или всего расчёта по двум вызовам определить нельзя.

## Что имеет смысл использовать

### 1. IPC Toolkit — основной кандидат для контакта

[IPC Toolkit 1.6.1](https://github.com/ipc-sim/ipc-toolkit/tree/v1.6.1) под
MIT-лицензией содержит поиск кандидатов, непрерывную проверку столкновений,
безопасную долю линейного шага, расстояния и геометрию контакта; в нём есть
также барьерные и фрикционные компоненты. Это **не готовый решатель ткани**.

Рекомендуемый объём для первой интеграции: использовать готовую библиотеку
для поиска контактов и CCD, а не писать собственную CCD с нуля. Локальный
ответ на контакт придётся согласовать с ограничениями существующего решателя:
сохранением размеров, стенки, закреплений и несколькими деталями. Общий
откат допустим как аварийная мера, но не как основной способ симуляции:
он может затормозить всю сетку и создать ложную «остановку».

Трение в текущем опыте — собственная упрощённая поправка; корректность закона
трения не установлена. Готовые фрикционные компоненты IPC разумно исследовать,
но они пока **не подключены и не проверены** в нашем решателе. Исходные
пересечения, полное вложение тела в опору, соседние примитивы и нелинейные
внутренние проекции требуют дополнительных проверок — CCD не универсальный
сертификат правильности.

Для самостоятельного Windows EXE пользователь не должен отдельно ставить
библиотеки. У официального `ipctk==1.6.1` есть Windows x64 wheel для Python
3.12; он требует NumPy и SciPy. Текущий `forma.spec` явно исключает SciPy и
IPC не включает. Ранее на Windows CI с Python импорт IPC и короткий опыт
прошли, но упаковка и запуск IPC **внутри EXE не проверены**. Самый прямой
путь — сначала проверить обычную упаковку wheel и зависимостей вместе с EXE,
включая сопутствующие DLL и лицензии. Компиляция только нужных частей C++ без
SciPy — возможная альтернатива, но её трудоёмкость и результат здесь не
измерены; не надо заранее обещать уменьшение или работоспособность сборки.

### 2. PositionBasedDynamics — источник проверенных ограничений, не замена вслепую

[PositionBasedDynamics](https://github.com/InteractiveComputerGraphics/PositionBasedDynamics/tree/10a70bc146a97873dc3c8fef372f5217e010542e)
лицензирована MIT. Доступна Python-библиотека `pypbd==2.2.2` с Windows x64
wheel; метаданные требуют NumPy, pygame и PyOpenGL. Отдельный тест в Linux с
заблокированным импортом pygame и OpenGL показал, что **две простые операции**
ядра работают без них; это не доказывает, что все функции или Windows EXE
можно упаковать без этих зависимостей.

В практическом тесте ограничение длины вернуло закреплённое ребро из длины
2 в исходную длину 1; неподвижная вершина осталась на месте. Для одного
сжатого тетраэдра с тремя закреплёнными вершинами ограничение объёма за 20
итераций восстановило высоту с 0,2 до 0,979 при исходной 1. Это демонстрация
полезных компонентов, а не тест ткани, толщины, контактов или возможности
достигнуть абсолютной точности за конечное число итераций:
[`pbd-simple-constraints-linux.json`](../benchmarks/drape_six/pbd-simple-constraints-linux.json).

В конкретном [детекторе расстояний](https://github.com/InteractiveComputerGraphics/PositionBasedDynamics/blob/10a70bc146a97873dc3c8fef372f5217e010542e/Simulation/DistanceFieldCollisionDetection.cpp#L34-L45)
пары одного объекта исключены с комментарием TODO о самоконтакте гибких тел.
Это не означает, что вся библиотека не способна к самоконтакту, и не
устанавливает точное соответствие исходников Python wheel. Но она не показала
себя готовой заменой нашего контактного решателя в шести сценах.

Практический выбор: изучать её реализации XPBD, изгиба и локального объёма,
при необходимости использовать подходящие части с соблюдением лицензий;
встраивать весь движок или заменять им `drape` только если отдельное сравнение
покажет преимущество. Сейчас такого сравнения нет.

### 3. Codim-IPC — запасной путь, не первая интеграция

[Codim-IPC](https://github.com/ipc-sim/Codim-IPC/tree/9c6cbe3a5bef09a967ca8d420056adfafdf1fc9a)
— отдельная исследовательская реализация; лицензия основного репозитория
Apache-2.0. README описывает сборку под Ubuntu и macOS; готовая Windows-сборка
и все лицензии зависимостей нами не проверены. Это потенциально интересный
резерв, если существующий решатель не удастся согласовать с надёжным
контактом, но на наших шести сценах он не запускался. Объявлять его лучшим
или встраивать целиком без проверки сейчас было бы преждевременно.

### 4. Средняя поверхность — выборочная оптимизация, не замена толщины

Для листа и некоторых парных оболочек расчёт средней поверхности может
уменьшить число частиц, но вернуть толщину без самопересечений и изменения
поверхности удаётся не всегда. Произвольные объёмные тела и неспаренные
стенки нельзя автоматически сводить к такой поверхности. Пользователь требует
сохранять толщину, поэтому этот режим рассматривается только для распознанных
геометрий и после проверки восстановленной оболочки; основной формат проекта
и исходная геометрия не заменяются.

При обычном изгибе слоя конечной толщины внешний путь длиннее внутреннего.
Поэтому для произвольных изгибов нельзя одновременно обещать абсолютно
неизменную толщину **и** абсолютно неизменную длину каждого поверхностного
ребра. Это не повод принимать большие искажения: величины нужно измерять,
ограничивать и согласовать допустимую численную погрешность; разрывы и
проникновение не должны маскироваться.

## Проверки и воспроизведение

Целевые тесты `test_drape_library_candidates.py`, `test_drape_ipc_bounded_probe.py`,
`test_drape_six_probe.py` и `test_drape_step_order.py`: **29 passed**.
Зависимости `ipctk`, `python-fcl` и `pypbd` устанавливались только в
изолированное исследовательское окружение; в требования и упаковку
приложения не добавлены.

```sh
OPENBLAS_NUM_THREADS=1 PYTHONPATH=forma timeout 75s python \
  forma/tools/drape_ipc_first_impact_probe.py --case 01_sheet_over_ball --output impact-ball.json
OPENBLAS_NUM_THREADS=1 PYTHONPATH=forma timeout 90s python \
  forma/tools/drape_ipc_first_impact_probe.py --case 06_sleeve_around_rod --output impact-rod.json
OPENBLAS_NUM_THREADS=1 timeout 20s python \
  forma/tools/drape_pbd_constraints_probe.py --output pbd.json
OPENBLAS_NUM_THREADS=1 PYTHONPATH=forma timeout 75s python -m pytest -q \
  forma/tests/test_drape_library_candidates.py forma/tests/test_drape_ipc_bounded_probe.py \
  forma/tests/test_drape_six_probe.py forma/tests/test_drape_step_order.py
```

Дальше нужно проверить не отдельные шаги, а устойчивый контакт и трение на
полной траектории, длины и толщину в совокупности, свисание скатерти,
закрепления и несколько подвижных частей. После успешной проверки всех шести
сцен и автономной Windows-упаковки можно собирать новый EXE.
