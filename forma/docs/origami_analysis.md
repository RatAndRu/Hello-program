# Оригами в ФОРМЕ: каталог складок, чего не хватает и как это обойти

Разбор по просьбе: методики сгиба с литературой, честный список «есть в коде /
нет в коде», шаг «сложить ради кромки, потом разогнуть», соединения без клея
и верёвки, способ просить нейросеть придумать оригами по теме, малоизвестные
приёмы.

Все числа в тексте получены прогоном сценариев через `build()` — скрипт
`docs/origami_probe.py` (запуск: `python docs/origami_probe.py`, ~1.5 минуты).
Схемы: `docs/img/origami_*.svg`, генератор `docs/make_origami_svg.py --check`.
Рабочие примеры: `examples/origami_crease.forma`, `examples/origami_hinge.forma`
(оба проходят все свои проверки — 3/3 и 4/4).

---

## 0. Короткий ответ

Движок умеет **физику одного перегиба**: лист гнётся по произвольной линии,
с радиусом, зазором между слоями и профилем ребра, объём при этом сохраняется
(3.18 см³ против 3.20 см³ у плоского листа). Он не умеет **оригами как
последовательность**: нет знака «долина/гора» как понятия, нет порядка складок,
нет разгиба, нет надрезов, нет линий сгиба на развёртке. Второй сгиб на
объёмной детали не строится ни в одном из 20 проверенных вариантов; на
почти плоской — строится в 17 из 20, но только если линию ставить по верху
габарита, а не по исходному листу.

Практический вывод: сегодняшняя «оригами-модель» — это либо **один сгиб на
листе**, либо **сборка из панелей на петлях** (`сопряжение type=петля`), либо
**лист с продавленными линиями** (`складка mode=канавка`) — то есть развёртка
для ручной работы, а не сложенная модель. Всё остальное в этом документе —
проект DSL и порядок работ, а не описание готовых возможностей.

## 1. Как устроена складка: минимум теории, который нужен программе

### 1.1 Долина и гора — это знак угла

Любой сгиб — это ребро, по которому две плоские части листа поворачиваются
друг относительно друга. Различают всего два знака: **долина** (valley) —
сгиб к себе, лист складывается «лодочкой», и **гора** (mountain) — от себя.
В системе условных обозначений Ёсидзавы–Рэндлетта (Yoshizawa–Randlett) это
штрих и штрих-пунктир; та же система задаёт стрелки «согнуть», «перевернуть»,
«утопить», «раскрыть» [1, 2].

Для программы это ровно один бит на складку: `side = ±1` или знак угла. Всё
остальное — следствие. Поэтому «долина/гора» — не отдельная команда, а
**обязательный атрибут** любой складки.

### 1.2 Три закона плоского складывания

Для вершины, где сходятся несколько складок на плоском листе, есть два
локальных закона и один набор аксиом построения.

| Закон | Формулировка | Что даёт программе |
|---|---|---|
| **Маэкава** (Maekawa) | в вершине разность числа гор и долин равна ±2: `M − V = ±2` | проверка «можно ли так сложить» за O(1), ловит половину ошибок развёртки |
| **Кавасаки** (Kawasaki) | сумма углов через один равна 180°: `α₁+α₃+… = α₂+α₄+… = 180°` | проверка вершины по координатам; необходимо и достаточно **локально** |
| **Хузита–Хатори** (Huzita–Hatori, 1989) | 7 аксиом: что вообще можно построить сгибом (через 2 точки, перпендикуляр, биссектриса, касание, …) | правила построения линий сгиба из точек и рёбер |

Оба закона локальные: они не гарантируют, что лист сложится целиком без
самопересечений — глобальная проверка плоскоскладываемости NP-полна [3, 4, 5].

### 1.3 Жёсткое оригами: складка как шарнир

Если бумагу считать жёсткими гранями на шарнирах («rigid origami»), у каждой
складки есть **угол складывания** (fold angle, 0 — плоско, π — сложено,
отрицательный — гора). Триангулированная модель имеет `N` рёбер и `M`
внутренних вершин; число степеней свободы `N − 3M`, а поведение считается
методом штрафных сил (Tachi) [6, 7]. Условие «вершина складывается жёстко»:
не меньше четырёх лучей, все секторы меньше π, вершина не «неопределённое
пересечение» (Demaine–O'Rourke) [8].

Именно эта модель и нужна CAD-движку: складка — шарнир, панель — жёсткая
пластина, лист — граф панелей и петель. И ровно её у нас реализует
`сопряжение type=петля`, а не `сгиб`.

### 1.4 Толщина: почему 7 сгибов — это предел

Формула Галливана (Britney Gallivan, 2001) для складывания полосы пополам `n`
раз при толщине `t`:

```
L = (π·t / 6) · (2ⁿ + 4) · (2ⁿ − 1)
```

При `t = 0,1 мм` семь сгибов требуют 0,88 м, а двенадцать — около 880 м;
в рекордном опыте на 12 сгибов ушло 1,2 км бумаги [9, 10]. То есть толщина — не косметика: она определяет, какие модели вообще
складываются, и именно её движок пока учитывает плохо (см. §3).

## 2. Каталог: что за складка и чем она строится

Схема — `docs/img/origami_folds.svg` (двенадцать видов с торца и статус
в движке).

### 2.1 Двенадцать складок

| Складка | Английский | Как строится физически | В ФОРМЕ |
|---|---|---|---|
| Долина | valley fold | один перегиб к себе | **есть**: `сгиб angle=…` (сторона по умолчанию) |
| Гора | mountain fold | тот же перегиб от себя | **есть фактически**: `side=−1` переставляет подвижную сторону; слова «гора» в DSL нет |
| Плиссе | pleat | две встречные складки, полотнище между ними | **нет** как такового: нужны две линии, а `сгиб` делает одну |
| Гармошка | accordion / fan | серия плиссе подряд | **есть**: `сгиб parts=3…12`, `fold_sheet parts` — только равные полотнища |
| Обратный внутрь | inside reverse fold | слой разворачивается, вершина уходит внутрь | **нет** |
| Обратный наружу | outside reverse fold | слой выворачивается наружу | **нет** |
| Сплющивание | squash fold | карман раскрывается и расплющивается по двум линиям | **нет** |
| Лепесток | petal fold | два «уха» через общую линию, слой вытягивается | **нет** |
| Ухо кролика | rabbit ear | три луча из одной точки, вершина тянется | **нет** |
| Утопление | sink (open/closed/double) | вершина вдавливается внутрь между слоями | **нет** |
| Кримп | crimp | две встречные складки со сдвигом по линии | **нет** |
| Изогнутая складка | curved fold | линия сгиба — дуга, лист гофрируется | **частично**: `складка bend=`, `corrugate`, но не дуга по развёртке |

Список складок и их определение — по сводкам [1, 11, 12]. Важно: восемь из
двенадцати — не «новый перегиб», а **перестановка слоёв**. Поэтому они и не
строятся одним поворотом сетки: нужен порядок слоёв, которого в модели нет.

### 2.2 Семь базовых форм

| База | Английский | Сгибов | Складки внутри |
|---|---|---:|---|
| Блин | blintz base | 4 | четыре долины к центру |
| Квадрат | preliminary base | 4 | диагонали + пополам, сплющивание |
| Водяная бомба | waterbomb base | 4 | обратные складки внутрь |
| Воздушный змей | kite base | 2 | долины к диагонали |
| Рыба | fish base | 4 | два уха кролика |
| Птица | bird base | 8 | лепесток + обратные внутрь |
| Лягушка | frog base | 10 | два лепестка |

Птица (bird) — основа журавлика; её растянутая и «блинцованная» версии
(stretched / blintzed bird base) дают длинные ноги и хвост [12, 13]. Для
машины из бумаги полезна не птица, а **водяная бомба** (объёмный купол) и
**квадрат** (симметричный корпус).

### 2.3 Технические складки (не про фигурки, а про конструкцию)

| Складка | Что даёт | В ФОРМЕ |
|---|---|---|
| **Миура-ори** (Miura-ori) | плоская складка с одной степенью свободы: тянется в одном направлении, жёсткая в другом; основа разворачиваемых конструкций | **нет** как слоистая складка; есть рельеф `corrugate mode=зигзаг` |
| **Водяная бомба** (waterbomb tessellation) | объёмная сетка, «сжимается» в двух направлениях | **нет** |
| **Ёсимура** (Yoshimura) | диагональная сетка, осевое сжатие цилиндра | **нет** |
| **Шестиугольные соты** | жёсткая жёсткость в плоскости, упаковка | **нет** |
| **Киригами** | надрезы + сгибы: раздвижные решётки, защёлки | **нет** надрезов |
| **Гофрирование** | рёбра жёсткости | **есть**: `corrugate` (гофра/вафля/рифление/зигзаг) — но это рельеф поверхности, а не слои |

Жёсткое поведение Миура-ори (одна степень свободы, кинематическая
определённость) — прямое следствие §1.3; для нашей задачи это главный
кандидат на «умную» складку, потому что она **не требует нового кода слоёв**:
это периодическая сетка, а её кинематику можно посчитать по углу [7, 8].

## 3. Что движок делает на самом деле (замеры, не обещания)

Лист 80×80×0,5 мм (объём 3,20 см³, 192 треугольника), если не указано иное.
Время — один вызов `build()` на этом же железе.

### 3.1 Один сгиб

| Сценарий | Время, с | Треугольников | Габарит, мм | Объём |
|---|---:|---:|---|---:|
| плоский лист | 0,02 | 192 | 80,0 × 80,0 × 0,5 | 3,20 |
| `сгиб 30°` | 1,21 | 136 | 80,0 × 74,6 × 20,4 | 3,21 |
| `сгиб 90°` | 1,16 | 748 | 80,0 × 40,1 × 40,1 | 3,19 |
| `сгиб 150°` | 1,18 | 1 444 | 80,0 × 39,8 × 20,8 | 3,17 |
| `сгиб 179°` | 1,15 | 1 944 | 80,0 × 39,6 × 1,9 | 3,18 |
| `сгиб 179° sharp=1 gap=0,05` | 3,09 | 5 888 | 80,0 × 39,9 × **1,21** | 3,17 |
| `складка` (канавка) r=0,4 depth=0,15 | 0,89 | 1 854 | 80,0 × 80,0 × 0,65 | 3,20 |

**Вывод 1.** `sharp=1` (профиль «пресс-биг») — не украшение: пакет из двух
слоёв занимает 1,21 мм вместо 1,93 мм при `sharp=0`, то есть 1,21 вместо
идеальных 1,0. По умолчанию `sharp=0`, поэтому «бумага» по умолчанию пухнет
почти вдвое. Для бумаги надо писать `sharp=1`.

**Вывод 2 (дефект).** При `angle ≤ 22°` сетка вырождается: остаётся 20–28
треугольников вместо тысяч. Внешне габарит «правильный», но это уже не лист,
а грубая оболочка. Поэтому «остаточный угол 3°» через `сгиб` невозможен — и
не только из-за минимума `angle ≥ 1`.

### 3.2 Слои: сколько сгибов реально складывается

| Способ | Слоёв | Идеал, мм | Факт по Z, мм | Итог |
|---|---:|---:|---:|---|
| `сгиб sharp=0` | 2 | 1,0 | 1,93 | ×1,93 |
| `сгиб sharp=1` | 2 | 1,0 | 1,21 | ×1,21 |
| второй `сгиб sharp=1` по верху bbox | 4 | 2,0 | **1,94** | ×0,97 — попадание |
| третий `сгиб sharp=1` | 8 | 4,0 | — | **«Линия сгиба не пересекает деталь»** |
| `fold` (половинное) дважды | 4 | 2,0 | 3,12 | ×1,56 |
| `fold` трижды | 8 | 4,0 | **0,56** | ×0,14 — молчаливая потеря геометрии |
| `fold parts=4` | 4 | 2,0 | 3,75 | ×1,88 |
| `fold_sheet parts=4 angle=179` | 4 | 2,0 | 4,90 | объём 5,64 вместо 3,20 (+76 %) |
| `сгиб parts=3` (гармошка) | 3 полотнища | — | 3,44 | объём сохранён |

**Вывод 3.** Максимум для `сгиб` — **два** сгиба, и только с `sharp=1`; четыре
слоя получаются с точностью 3 %. Третий сгиб не строится. У `fold` хуже:
третий вызов не падает, а возвращает плоскую «лепёшку» 0,56 мм на восемь
слоёв — ошибку надо ловить проверкой габарита, сама команда молчит.

**Вывод 4 (дефект).** Гармошка `parts` сохраняет объём у `сгиб`, но
`fold_sheet parts=4` раздувает объём на 76 %: это не физика, а растяжение
сетки. В промпте это надо помнить: «объём сохранился» — не гарантия.

### 3.3 Второй сгиб: где он вообще возможен

| Условие | Работает |
|---|---|
| первый сгиб 120°, `at` на плоскости исходного листа | **0 из 20**: 17× «На плоскую часть листа остаётся 0,0 мм, а сгиб занимает 91,7 мм», 3× «не пересекает деталь» |
| первый сгиб 179°, `at` = верх габарита текущей детали | **17 из 20** |
| третий сгиб по верху габарита | 3 из 6 |

**Правило, которое надо зашить в движок:** `at` следующего сгиба — не точка
исходного листа, а **верх`bbox` текущей детали** (и на волос ниже верхней
грани). Именно это превращает 0/20 в 17/20. Сейчас правило знает человек,
а не программа.

### 3.4 Разгиб

| Попытка | Итог |
|---|---|
| тот же `side` | «Линия сгиба не пересекает деталь» |
| `side=−1` | «Линия сгиба не пересекает деталь» |
| линия на верхней плоскости | «Линия сгиба не пересекает деталь» |

Разгиба нет: `сгиб` строит новую геометрию из исходной, а не «отматывает»
предыдущую, и после первого сгиба линия привязывается к новому габариту.

### 3.5 Панели и петли: обходной путь, который работает

| Сценарий | Габарит | Род | Комментарий |
|---|---|---:|---|
| две панели, петля 179°, `point` на нижней грани | 1,02 мм по Z | 0 | идеал 1,0; пересечений 0 |
| две панели, петля 100°, `point` на середине толщины | «уголок» | — | остаток связи 0,3 мм ≤ 1 мм — держится |
| две панели, петля 100°, `point` не на кромке | — | — | остаток 5,0 мм — «разъехалась» |
| четыре панели, три петли подряд | 1,55 мм | **−2** | 1 пара пересечений 467 мм³: ось второй петли задана абсолютно и не пересчитывается после поворота соседа |

**Вывод 5.** Петля честно работает для **одной** складки и требует `point`
ровно на линии сгиба (на кромке, в середине толщины). Цепочка петель требует
пересчёта осей — это не «сопряжение», а кинематика, и её в движке нет.

## 4. Чего не хватает в DSL

Разбор по пунктам: что есть сейчас, что нужно, зачем. Цена указана в знаках
промпта: одна команда в инструкции — около 343 знаков (≈107 токенов), в
полном каталоге — 1 173 знака (≈367 токенов). Поэтому везде, где можно
обойтись **параметром существующей команды**, новой команды быть не должно.

### 4.1 Знак складки (долина/гора)

Сейчас есть только `side` — какая сторона подвижная. Это не то же самое, что
знак складки: «гора» — свойство ребра, а `side` — выбор половины листа.
Слова «долина» нет ни в инструкции, ни в поиске по реестру. Предложение:

```
сгиб лист at=… dir=… angle=120 вид=долина
сгиб лист at=… dir=… angle=120 вид=гора
```

Цена: один параметр, 0 новых команд. Обоснование: термин из стандарта
Yoshizawa–Randlett [1], нейросеть и человек ищут именно эти слова.

### 4.2 Автоподъём линии сгиба

Сейчас: ошибку «остаётся 0,0 мм» дают 17 из 20 попыток. Предложение:
`at=верх` (или `подъём=авто`) — линия ставится на верх `bbox` детали.

Цена: 0 новых команд, параметр-режим. Это правило из §3.3, то есть
**единственное изменение, которое сразу делает возможным второй сгиб**.

### 4.3 Порядок складок и слои

Сейчас: каждый `сгиб` — независимая деформация, истории нет. Нужна не
команда, а **структура сценария**:

```
складки {
  шаг 1: сгиб … вид=долина
  шаг 2: перевернуть
  шаг 3: сгиб … вид=гора
  шаг 4: раскрыть слой 2
}
```

Зачем: без порядка нет ни пошаговой анимации, ни видеоинструкции, ни проверки
«складывается ли модель вообще». Это же требуется и для ИИ-пайплайна (§7):
модель должна выдавать шаги, а не готовую сетку.

### 4.4 Разгиб и префолд

Сейчас: `angle ≥ 1`, разгиба нет. Нужны два разных понятия:

| Понятие | Что значит | Реализация |
|---|---|---|
| **разгиб** | вернуть лист в плоскость, оставив память о сгибе | новая операция: обратный ход по записанному шагу |
| **префолд / биг / риск** | продавить линию, не складывая | **уже есть**: `складка mode=канавка` |

Практический вывод: «сложить и разогнуть» сегодня выражается **только**
канавкой (§5).

### 4.5 Надрез (киригами)

Сейчас: `cut shape=sphere|box|cylinder|cone|ring` — вырезание объёма, но нет
разреза **нулевой ширины** по линии. Нужно `надрез from=[…] to=[…]` или
`cut shape=плоскость`. Зачем: киригами-решётки, защёлки, раздвижные механизмы
без клея.

### 4.6 Линии сгиба на развёртке

Сейчас: `section` даёт 2D-контур (DXF и SVG), но **без линий сгиба** и без
разметки гора/долина. Для печати развёртки нужен экспорт «контур + линии
сгиба с типом». Стандарт де-факто: формат **FOLD** (JSON) и файлы
`.cp`/`.opx` редактора ORIPA (типы линий: 1 — контур, 2 — гора, 3 — долина)
[14, 15]. Это дешевле, чем любой собственный формат: экспорт в `.cp` — это
несколько строк.

### 4.7 Толщина и зазоры слоёв

Сейчас: `gap` есть, `sharp` есть, но по умолчанию пакет пухнет вдвое, а
проверки «толщина пакета» нет. Нужно: `толщина_пакета` как правило проверки
(сколько слоёв × толщина ± допуск) и `sharp=1` в примерах по умолчанию.
Для сравнения: идеал для 4 слоёв 0,5 мм — 2,0 мм, факт при `sharp=1` — 1,94,
при `sharp=0` — 4,17.

### 4.8 Соединение слоёв

Сейчас: нет. Слои просто лежат друг на друге с зазором `gap`. Нужен хотя бы
один тип «зажим» (`замок`): язычок входит в карман и держится трением.
Физика — §6.

### 4.9 Мятая бумага

Сейчас: `corrugate` даёт правильный рельеф (гофра, вафля, рифление, зигзаг),
`drape` — ткань. «Мятой» бумаги (случайный изгиб с памятью) нет. Приоритет
низкий: для модели это почти всегда дефект, а не замысел.

### 4.10 Сводка приоритетов

Критерий приоритета — тот же, что в аудите реестра: стандарт с таблицей,
сборка длиннее 6 операций, частота выше 5 %, проверяемость.

| № | Что | Тип | Цена | Приоритет |
|---|---|---|---:|---|
| 1 | `вид=долина/гора` | параметр | 0 команд | **P0** |
| 2 | `at=верх` (авто по bbox) | параметр | 0 команд | **P0** |
| 3 | `sharp=1` в справке и в обоих примерах | документация | 0 | **P0** |
| 4 | алиас `оригами` → `сгиб` (сейчас ведёт на `fold`) | 1 строка | 0 | **P0** |
| 5 | `префолд` как алиас `складка mode=канавка` | алиас | 0 | **P0** |
| 6 | блок `складки { шаг … }` + история | структура | 1 команда | **P1** |
| 7 | `разгиб` | команда | ≈107 токенов | **P1** |
| 8 | экспорт `.cp` / FOLD | экспорт | ≈107 | **P1** |
| 9 | `надрез` | команда | ≈107 | **P1** |
| 10 | проверка «толщина пакета» | правило | ≈40 | **P1** |
| 11 | `замок` (язычок + карман + проверка) | команда-макрос | ≈150 | **P2** |
| 12 | кинематика цепочки петель | модель | — | **P2** |
| 13 | `вкладыш` (каркас внутри) | параметр | ≈40 | **P2** |

Итого P0 — пять правок без новых команд, P1 — пять позиций, из них три
новые команды (≈320 токенов каталога, 0,4 % реестра). Для сравнения: полный
каталог 227 команд — около 83 000 токенов, то есть добавка не меняет порядок
величины, но и не должна расти без проверки полноты.

## 5. «Сложить ради кромки, потом разогнуть» — отдельный шаг

Схема: `docs/img/origami_fold_unfold.svg`.

### 5.1 Почему это не то же самое, что сгиб

Физика шага в пяти состояниях:

1. **лист** — плоско, памяти нет;
2. **сложить** — угол ≈179°, слои легли, ребро сформировано;
3. **загладить** — то же плюс давление: волокна смяты по линии (костяная
   папка, биговка, ноготь) [16];
4. **разогнуть** — угол 2…5°: остаётся **остаточный угол** — бумага «помнит»
   (в модели это выражается канавкой: `сгиб` при угле ≤ 22° вырождает сетку, §3.1);
5. **кромка** — плоско, но по линии видна канавка: дальше лист складывается
   точно по ней и не «гуляет».

Разница принципиальная: после шага 5 деталь **плоская**, значит её можно
печатать, класть в развёртку и складывать руками. Это и есть смысл
«префолда» в реальных инструкциях — он есть почти в каждой модели, но в
наших сценариях его нечем записать.

### 5.2 Что уже есть и чего не хватает

| Нужно | Есть сегодня |
|---|---|
| продавить линию, не складывая | **да**: `складка … mode=канавка r=0.4 depth=0.15` |
| увидеть линию на детали | **да**: канавка видна в геометрии (глубина 0,15 мм) |
| сложить по продавленной линии | **да**: `сгиб` по той же линии (проверено: биг → сгиб 2,31 с) |
| вернуть лист в плоскость | **нет**: три попытки → «Линия сгиба не пересекает деталь» |
| записать шаг в историю как отдельный | **нет**: истории шагов нет |
| показать шаг в анимации | **нет**: `morph` есть, но см. §5.4 |

### 5.3 Как записывать (предложение DSL)

```
лист = sheet width=160 length=160 thickness=0.5
префолд лист from=[-80,0,0.5] to=[80,0,0.5] r=0.4 depth=0.25 passes=2
префолд лист from=[0,-80,0.5] to=[0,80,0.5] r=0.4 depth=0.25
сгиб лист at=[0,0,0.5] dir=0 angle=179 sharp=1 gap=0.05 unfold=да rest=3
```

Три новых параметра (`unfold`, `rest`, `passes`) и один алиас (`префолд`).
`passes=2` — «сколько раз прогладили»: при двух проходах канавка глубже, и
это надо уметь выразить, потому что в инструкциях это отдельная строчка
(«прогладить ещё раз»).

### 5.4 Анимация: где шаг живёт и куда не попадает

`animate kind=morph param=A from=1 to=180` строит кадры **пересборкой
сценария** (один кадр — 0,89 с на 20 треугольниках; 24 кадра трёхсекундного
ролика — около 21 с). Ограничения, проверенные прогоном:

- `from=0` невозможно: у `сгиб` минимум `angle=1`;
- кадры считает только `webui.morph()` по HTTP — через `build()` морфинг не
  проверить;
- `add_glb_animations` понимает `spin / formation / explode / move / scale /
  turn`, а `morph`, `assembly` и `wait` **отбрасывает** — значит складывание
  в GLB не экспортируется, оно живёт только в окне приложения.

Отсюда требование к шагу «сложить-разогнуть»: он должен быть **отдельным
кадром истории** (`шаг`), а не побочным эффектом `angle`. Иначе видеоинструкция
пропустит физически важное действие.

## 6. Соединения без клея и верёвки

Схема: `docs/img/origami_joints.svg`. Шесть механизмов сводятся к трём
числам: **натяг**, **заход**, **зазор**. Все три в движке уже есть — как
проверки, а не как конструктор.

| Механизм | Геометрия | Числа | Чем проверять | В ФОРМЕ |
|---|---|---|---|---|
| Клапан в карман (tab-and-pocket) | ухо входит в карман, зажимается двумя слоями | ухо 8…12 мм, глубина ≥ ухо + 2t, зазор 0,1…0,3 | `inside` + `gap` | **геометрия вручную**, проверка есть |
| Замок коробки (tuck lock) | клапан подсовывается под поясок | вылет ≥ ширина + 2t, заход 6…8 мм | `gap` | вручную |
| Складка-замок (pleat lock) | две встречные складки цепляются | шаг 2t…3t, сдвиг шаг/2 | `gap` | вручную (`сгиб parts`) |
| Клин / ласточкин хвост | трапеция входит в паз | скос 5…15°, зазор 0,15 | `gap` + `draft` | **геометрия вручную**: `cut` + `draft`, проверка `gap` |
| Фрикционная посадка | держится на натяге | натяг 0,05…0,15, длина ≥ 3t | `interference` | через пересечение |
| Скрутка (roll rivet) | трубка из скрученной бумаги стягивает пакет | D 3…5 мм, витков ≥ 3 | `wall` + `gap` | вручную (`pipe`, `sheet roll`) |

Источники по механизмам: модульное оригами и его замки (Sonobe, Penultimate)
[17, 18], коробки с замком [19].

### 6.1 Что проверено прогоном

```
плита = sheet width=60 length=60 thickness=2
с_пазом = cut плита shape=box at=[0,0,1] size=[20.6,4.6,3]
шип = box size=[20,4,2] center=да at=[0,0,1]
проверка шип gap с_пазом 0.1..0.5
```

Результат: «зазор до «с_пазом»: 0,3 мм (в норме, нужно от 0,1 до 0,5 мм)»;
род детали с пазом — 1 (`проверить с_пазом genus 1` → «сквозные отверстия: 1 —
в норме»). То есть **паз как геометрия делается** (`cut`), а как понятие
(`паз`) существует только в сопряжениях: `сопряжение b a type=паз` ставит
деталь на рейку, остаток 0 мм.

Что не получается без доработки:

- **натяг** не выразить: `gap` измеряет расстояние и не бывает отрицательным;
  пересечение ловится только `interference`: кубик 4×4×4, утопленный в плиту
  на 1 мм, даёт 16 мм³ пересечения — то есть «натяг» видно, но только как
  дефект;
- **колесо на ось** по умолчанию вдвигается в корпус: `сопряжение к1 капот
  type=ось axis=x` при любом `offset` дал 352 мм³ пересечения — параметра
  «вынести наружу» нет;
- **язычок-защёлка** (киригами) невозможна: нет надрезов (§4.5).

### 6.2 Правила, которые стоит зашить в автоподбор

Для бумаги толщиной `t`:

1. зазор посадки `0,1…0,3 мм` (меньше — не соберётся, больше — вывалится);
2. заход язычка `≥ 3t`, выступ `6…8 мм`;
3. фрикционная посадка работает только от картона (`t ≥ 0,8 мм`), для
   бумаги 0,1 мм нужен замок, а не трение;
4. если деталь должна «держаться», а не «стоять», нужна проверка
   `связь` — иначе после правки всё разъедется молча.

## 7. Как просить нейросеть придумать оригами по теме

Схема: `docs/img/origami_ai_pipeline.svg`.

### 7.1 Главное, что известно из литературы 2025–2026

| Работа | Что показала | Цифры |
|---|---|---|
| **COrigami** (arXiv 2606.26299, DeepMind + Р. Лэнг, 2026) | пайплайн «текст → палочковая схема → упаковка кругов → развёртка → формовка → оценка»; развёртка = отрезки + гора/долина + доля сгиба | обучено на ~100 моделях; при прямом дообучении на развёртках потолок ≈60 % плоскоскладываемости |
| **OrigamiSpace** (arXiv 2511.18450, NeurIPS 2025) | 350 задач, 1 500 вопросов, 120 задач генерации развёрток | GPT-4o 42–52 %, эксперт 98–100 %; 10 раундов обратной связи от компилятора подняли успех 28,6 % → 66,9 % |
| **OrigamiBench** (arXiv 2603.13856, 2026) | ассоциативные задачи решаются легко, причинные — плохо | 96,18 % против 43,37 % при случайном уровне 25 % |

Три вывода, которые меняют постановку задачи:

1. **Просить развёртку целиком бесполезно** — даже специально обученные
   модели упираются в 60 %, а универсальные дают 42–52 %.
2. **Обратная связь от компилятора решает больше, чем модель**: тот же
   GPT-4o вырос с 28,6 % до 66,9 %, когда ему возвращали ошибки проверок.
   Значит наши проверки (Маэкава, Кавасаки, зазоры, род) — не придирки, а
   основной механизм качества.
3. **Причинные вопросы — слабое место**: «что будет, если сложить так»
   модель отвечает на уровне случайности. Поэтому шаги складывания должен
   считать алгоритм, а модель — придумывать образ и оценивать вид.

### 7.2 Методика: семь шагов, кто что делает

| Шаг | Делает | Что на выходе |
|---|---|---|
| 1. Тема | ИИ | «оригами машины» → характерные признаки: корпус, капот под углом, 4 колеса, лобовое стекло |
| 2. Палочковая схема | ИИ | граф из 6 лучей: центр + 4 колеса + стекло; длины в долях |
| 3. Упаковка | алгоритм | сколько площади листа нужно (дерево, упаковка кругов [23]) |
| 4. Развёртка | алгоритм | линии + гора/долина по правилам §1.2 |
| 5. Шаги | алгоритм + базы | 12–20 шагов в дереве складок |
| 6. Проверка | проверки движка | Маэкава, Кавасаки, слои, зазоры, род, габарит |
| 7. Оценка вида | ИИ | силуэт с 4 сторон, критика «похоже/не похоже» |

### 7.3 Формат промпта

```
Тема: оригами машины. Ограничения: один квадратный лист 150×150 мм,
без клея и надрезов (чистое оригами), модель должна стоять на столе.

Верни ТОЛЬКО:
1) палочковую схему: узлы (имя, x, y в долях листа), рёбра (что к чему);
2) список 12–20 шагов складывания: на каждом шаге — линия (две точки в
   координатах развёртки), тип (долина/гора), что с чем совмещается;
3) три числа: высота, длина, ширина готовой модели в мм.

Не рисуй развёртку и не считай её геометрию: линии посчитает компилятор,
ты отвечаешь за образ, пропорции и порядок.
```

Дальше — цикл: компилятор строит, проверки возвращают список нарушений
(«вершина 3: M−V = 0, нужно ±2»), модель правит шаги. Это ровно тот
механизм, который в OrigamiSpace дал +38 процентных пунктов.

### 7.4 Как это ложится в DSL

То, что можно собрать **сегодня**, без ожидания новых команд, — панельная
модель. Проверенный скелет (`examples/origami_hinge.forma`, 4/4 проверки):

```
капот = sheet width=60 length=70 thickness=0.6 at=[0,-30.3,0]
салон = sheet width=60 length=70 thickness=0.6 at=[0,30.3,0]
сопряжение салон капот type=петля axis=x angle=100 point=[0,0,0.3]
проверить салон связь
```

То, что нужно для настоящего оригами, — дерево складок (§4.3), и его пока
нет. Поэтому честная формулировка для пользователя: «сейчас ИИ может
придумать панельную модель с петлями и развёртку с линиями бига; сложенную
оригами-модель — после P1».

### 7.5 Критерии приёмки результата ИИ

1. **Плоскоскладываемость**: все вершины проходят Маэкаву и Кавасаки
   (локально), рекурсивный кримп не находит противоречий.
2. **Слои**: толщина пакета в самой толстой точке ≤ 4·t (±10 %).
3. **Стоит**: центр масс внутри опоры, плоское дно, `flat_bottom`.
4. **Печатается**: `wall ≥ 0,8 мм`, `overhang ≤ 45°`, `genus` ожидаемый.
5. **Похоже**: силуэт с 4 сторон совпадает с эскизом по `deviation`.
6. **Не врёт**: ни одна проверка не «неизвестное правило», каждая — с числом.

## 8. Малоизвестные приёмы, которые реально держат модель

| Приём | Что делает | Числа и как повторять |
|---|---|---|
| **Каркас внутри слоёв** | проволока 0,8–1,5 мм или скрученная бумага вставляется между слоями до финального складывания | держит шею журавлика, ноги, антенны; в модели — `pipe` + проверка `inside` |
| **Вкладыш (объём)** | внутрь корпуса вставляется распорка из картона или пенокартона | даёт объём, которого бумага не держит; `cardboard` + `inside` |
| **Фольга / двухслойная бумага** | бумага + алюминиевая фольга: держит форму, «не пружинит» | классика «tissue foil»; держит изгиб, где обычная бумага распрямляется [20, 21] |
| **MC / разбавленный ПВА** | метилцеллюлоза или разбавленный ПВА пропитывают готовую модель | фиксирует форму; сохнет десятки минут [20] |
| **Wet folding** | складывание влажной бумаги (толстая, 100–160 г/м²) | плавные кривые, «скульптурные» модели; сохнет под формой |
| **Утяжеление низа** | груз в нижней складке (монета, шайба, песок) | центр масс внизу → модель стоит; в модели — `масса` и `position` |
| **Распорка** | треугольная вставка между стенками изнутри | убирает «схлопывание» коробки; в модели — `inside` + `wall` |
| **Натяг / натянутая складка** | складка натягивается после сборки, замок затягивается | так держатся модульные шары без клея |
| **Чистое оригами** | без надрезов и клея (правило Akira Yoshizawa) | критерий выбора: если без надреза не выходит — менять схему, а не добавлять надрез |
| **Скрытая складка** | складка под существующим слоем, не видна снаружи | нужен порядок слоёв (§4.3) |

## 9. Итог: что делать в каком порядке

**Сейчас (без кода):**

- для одного сгиба — `сгиб … angle=179 sharp=1 gap=0.05`, `at` по верху
  габарита;
- для нескольких сгибов — панели + `сопряжение type=петля`, `point` на
  кромке;
- для «линии без складки» — `складка mode=канавка` (это и есть префолд);
- для соединения — `cut` (паз) + проверка `gap` + `сопряжение type=паз`;
- для развёртки — `section` (DXF и SVG), но без линий сгиба.

**P0 (пять правок, ноль новых команд):** `вид=долина/гора`, `at=верх`,
`sharp=1` в справке и примерах, алиас `оригами` → `сгиб` (сейчас `оригами`
ведёт на слабый `fold`, хотя инструкция советует `сгиб` — это прямая
несогласованность), плюс `префолд` как алиас канавки.

**P1:** дерево складок с шагами и историей, `разгиб`, экспорт `.cp`/FOLD,
`надрез`, проверка толщины пакета.

**P2:** `замок`, кинематика цепочек петель, `вкладыш`.

## Приложение А. Как воспроизвести замеры

```bash
cd forma
python docs/origami_probe.py            # таблицы §3.1–3.3 и 3.5
python docs/make_origami_svg.py --check # схемы + геометрическая проверка подписей
```

Скрипт замера ничего не меняет в движке: только `build()` и чтение
`analysis["metrics"]`. Проверка схем считает ширину строк по настоящему
шрифту DejaVu (PIL), поэтому «вылезание» подписи и наезд текстов ловятся
автоматически; без PIL включается грубая оценка по числу знаков.

Отдельно, вручную, для §3.2 — цепочка сгибов с `sharp=1` и линией по верху
габарита:

```python
s = "л = sheet width=80 length=80 thickness=0.5\n"
r = build(s)
z = r.analysis["metrics"]["bbox"][5]
s += f"f1 = сгиб л at=[0,0,{z}] dir=90 angle=179 sharp=1 gap=0.05\n"
```

Второй сгиб даёт 1,94 мм на четыре слоя; третий — ошибку «Линия сгиба не
пересекает деталь».
