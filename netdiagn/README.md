# 🩺 NET DOCTOR — почему телефон не видит мой Python-сервер

Один файл — [`net_doctor.py`](net_doctor.py). Только стандартная библиотека Python 3.8+,
никаких `pip install`. Русский интерфейс, подробные подсказки на каждом шаге.

[![NET DOCTOR — самотесты](https://github.com/RatAndRu/Hello-program/actions/workflows/netdoctor-tests.yml/badge.svg)](https://github.com/RatAndRu/Hello-program/actions/workflows/netdoctor-tests.yml)

---

## Ситуация, для которой он сделан

На ноутбуке (Windows) работает свой Python-сервер, например `http://192.168.0.60:5000/`.
На самом ноутбуке всё открывается — и по `127.0.0.1`, и по `192.168.0.60`.
А с телефона в той же Wi-Fi сети — **нет**. Раньше работало, сломалось «само»
(например, после отпуска с чужим Wi-Fi и экспериментов с VPN/1.1.1.1 WARP).

Инструмент не гадает: он идёт по цепочке

```
[Python-сервер] → [ноутбук: адрес + брандмауэр] → [Wi-Fi/роутер] → [телефон]
```

и показывает, **на каком именно этапе обрыв**.

## Запуск

| Что нужно | Как |
|---|---|
| 🖱️ **Windows, двойной клик** | [`start_netdoctor.vbs`](start_netdoctor.vbs) — основной способ |
| 🖱️ Резерв (если `.vbs` запрещён политикой) | [`start_netdoctor.bat`](start_netdoctor.bat) |
| ⌨️ Вручную | `python net_doctor.py` |
| 🔎 Проверить **свой** сервер на порту 5000 | `python net_doctor.py --check-port 5000` |
| 📱 Указать адрес телефона | `python net_doctor.py --phone 192.168.0.61` |
| 🛠️ Сразу подготовить починку | `python net_doctor.py --fix` |
| 🧪 Проверить сам инструмент | `python net_doctor.py --selftest` |

По умолчанию инструмент поднимает **тестовый сервер на порту 8770**, слушающий `0.0.0.0`,
печатает адреса и QR-код, и **ждёт запрос с телефона**. Если телефон открыл страницу —
канал жив, и проблема в самом приложении (чаще всего `host='127.0.0.1'`).

### Почему запуск через `.vbs`, а не через `.bat`

Первая версия лаунчера была `.bat`-файлом, и на Windows он мог показывать такое:

```
'on' is not recognized as an internal or external command,
'taйте' is not recognized as an internal or external command,
'*' is not recognized as an internal or external command,
'--------------------------------------' is not recognized as an internal or external command,
```

Это не «вирус» и не поломка Python — это **cmd.exe выполнял обрывки строк** внутри
`.bat`-файла. Причина — сочетание трёх вещей: кириллица в файле, юниксовые переводы
строк (LF) и команда `chcp` внутри скрипта. После смены кодовой страницы `cmd.exe`
перечитывает файл по неверному смещению (байты против символов) и исполняет куски
соседних строк как команды.

Что сделано, чтобы это не повторялось:

* **основной лаунчер теперь `.vbs`** — VBScript не зависит ни от кодовой страницы,
  ни от переводов строк, поэтому русские окна и пути с кириллицей работают надёжно;
* `.bat` оставлен только как резерв и переписан так, чтобы сломаться не мог:
  **только ASCII**, без BOM, без `chcp`, переводы строк CRLF;
* сам `net_doctor.py` включает UTF-8 в консоли программно (`setup_console`),
  поэтому `chcp` в файлах-лаунчерах больше не нужен вообще;
* в корне репозитория добавлен `.gitattributes`: `*.bat`, `*.cmd`, `*.vbs`, `*.ps1`
  всегда выкладываются в рабочую копию с CRLF;
* гигиена лаунчеров проверяется автотестами (`--selftest`), включая «плохой» пример,
  на котором проверка обязана сработать.

## Как читать результат

В конце печатается таблица «ЦЕПОЧКА: ГДЕ ПРОВАЛ» из 8 этапов:

| # | Этап | Если ✖ / ! | Что это значит и что делать |
|---|------|-----------|------------------------------|
| 1 | Получены адреса | адрес вида `169.254.*` | Ноутбук не получил IP от роутера: «забыть» Wi-Fi и подключиться заново |
| 2 | Профиль сети | Public (общедоступная) | Windows режет входящие. Лечится: `--fix` (переключит на Private) |
| 3 | Брандмауэр | «блокировать все входящие» | Даже разрешающие правила не помогут — снять галочку в `wf.msc` |
| 4 | Разрешение для `python.exe` | правила нет | Windows спросила «Разрешить доступ?» и когда-то ответили «Отмена» → `--fix` |
| 5 | Порт свободен и мы его слушаем | порт занят | Запущен другой экземпляр/чужой процесс → `--check-port <порт>` |
| 6 | Ответ по `127.0.0.1` | нет ответа | Проблема в самом Python-приложении, а не в сети |
| 7 | Ответ по `192.168.x.x` | нет ответа | Сеть/адрес; при APIPA-адресе телефон и не сможет достучаться |
| 8 | **Запрос с другого устройства** | не пришёл | Обрыв на участке «телефон → роутер → ноутбук»: WARP/VPN, гостевая сеть, изоляция клиентов |

### Три вещи, которые появились после реального «разбора полётов»

1. **Правильный адрес для телефона (и QR).** На ноутбуке обычно 5–7 адресов: Wi-Fi,
   мобильный хот-спот `192.168.137.1`, VMware `169.254.*`, Bluetooth. Инструмент
   сортирует их по пригодности и предлагает телефону только «живой» адрес Wi-Fi,
   а служебные прямо помечает как заведомо бесполезные. Раньше QR вёл на первый
   не-APIPA адрес — то есть мог вести в никуда.
2. **Контрольный тест закрытого порта.** Вместе с адресом печатается ссылка на
   заведомо закрытый порт. Это самый быстрый способ понять, где обрыв:
   «Отказано в подключении» → пакеты **доходят** до ноутбука (значит режет сам
   ноутбук: брандмауэр/антивирус); «Время ожидания истекло» → пакеты **не доходят**
   (роутер, гостевая сеть/изоляция клиентов, VPN на телефоне).
3. **Видно попытки «по https».** Если телефон открывал `https://…`, браузеры шлют
   TLS-приветствие — раньше HTTP-сервер молча отвечал ошибкой, и в журнале было
   пусто, будто «телефон не достучался». Теперь такая попытка распознаётся
   (`TLS ClientHello — открывали https://, а сервер ждёт http://`) и попадает
   в вердикт: сеть работает, дело в адресе.

Ещё в отчёте есть отдельные разделы: почему выбран этот адрес, какие правила
брандмауэра относятся к Python (с `RemoteAddress` — покрывают ли они **вашу**
подсеть), и журнал блокировок брандмауэра с подсказкой, как его включить.

### Если Python установлено несколько версий

Правило брандмауэра действует не «на Python вообще», а на **конкретный файл `.exe`**.
Поэтому инструмент теперь сопоставляет реальные пути слушающих процессов с путями
в правилах и печатает это отдельной строкой:

```
Python-процессы и правила брандмауэра   0.0.0.0:5000 (PID 42776) — правила нет:
    C:\...\pythoncore-3.14-64\pythonw.exe · правила есть для: C:\...\Python312-32\python.exe
```

В отчёте — раздел «PYTHON: КТО СЛУШАЕТ ПОРТЫ И ПОКРЫТ ЛИ ПРАВИЛАМИ» и список
установленных версий (`py -0p`). `--fix` добавляет правило для того интерпретатора,
который **реально слушает порт**, а не «для первого python из PATH».

## Топ-5 причин именно «после отпуска» (и лечение)

1. **Cloudflare WARP / 1.1.1.1 оставил службу и виртуальный адаптер.** WARP ломает
   входящие из локальной сети, при этом на самом ноутбуке всё открывается. Важно:
   служба `CloudflareWARP` в состоянии «Работает» — это ещё **не** признак активного
   туннеля; инструмент отдельно спрашивает `warp-cli status` и ищет скрытый адаптер.
   Проверьте: трей (правый нижний угол) → значок Cloudflare → выход; `services.msc` →
   служба `CloudflareWARP`; «Сетевые подключения» (`ncpa.cpl`) → адаптер `Cloudflare WARP`.
   Способ проверки «в лоб»: отключить WARP (`warp-cli disconnect`) и повторить тест.
1b. **Антивирус со своим сетевым экраном (ESET, Kaspersky, Malwarebytes).** Он фильтрует
   входящие независимо от брандмауэра Windows — правила Windows при этом могут быть
   идеальными. Проверка: выключить у антивируса «фильтрацию сетевых подключений/
   файрвол» на 2 минуты и сразу открыть адрес с телефона.
1c. **Включён мобильный хот-спот Windows.** Появляется адрес `192.168.137.1` и адаптер
   «Подключение по локальной сети*» — телефон в домашней Wi-Fi туда не попадёт, это
   другая подсеть. Отключите хот-спот (Параметры → Мобильный хот-спот), чтобы не путать
   адреса.
2. **Сеть снова помечена как «Общедоступная».** При подключении к чужому Wi-Fi Windows
   ставит профиль Public и блокирует входящие. Лечение: Параметры → Сеть и Интернет →
   Wi-Fi → свойства сети → «Частная», либо `--fix`.
3. **Нет правила брандмауэра для `python.exe`** (или правило только для Private-профиля).
   Обычно разрешение появляется в момент первого окна «Разрешить доступ». Если его
   отклонили — входящие тихо режутся. Лечение: `--fix`.
4. **Сервер слушает только `127.0.0.1`.** Тогда он виден только самому ноутбуку.
   В коде должно быть `host='0.0.0.0'` (Flask: `app.run(host='0.0.0.0', port=5000)`,
   стандартный `http.server`: `HTTPServer(('0.0.0.0', 5000), ...)`).
5. **Роутер: гостевая сеть или изоляция клиентов.** Телефон в «гостевом» SSID или
   на роутере включена изоляция — устройства друг друга не видят. Проверка: сравнить
   SSID и первые три числа IP на телефоне и ноутбуке; временно отключить «Guest
   network» / «AP isolation» в роутере.

## Если помогло выключение брандмауэра — верните его и сделайте правила

Выключенный брандмауэр действительно «лечит» проблему, но оставлять его выключенным нельзя:
на всех сетях открыт весь входящий трафик. Правильное решение — включить брандмауэр и
разрешить **конкретным файлам** то, что нужно, **только для своей локальной подсети**:

```powershell
# 1) вернуть брандмауэр (нужны права администратора)
Set-NetFirewallProfile -Profile Domain,Public,Private -Enabled True

# 2) узнать, какие файлы реально слушают ваши порты
Get-NetTCPConnection -State Listen | Where-Object LocalPort -in 5000,5001 |
  ForEach-Object { $p = Get-Process -Id $_.OwningProcess
    [pscustomobject]@{ Порт=$_.LocalPort; Процесс=$p.ProcessName; Файл=$p.Path } }

# 3) разрешить эти файлы и порты только своей локальной сети
Get-Process python,pythonw -ErrorAction SilentlyContinue |
  Select-Object -ExpandProperty Path -Unique | ForEach-Object {
    New-NetFirewallRule -DisplayName "Разрешить Python (LAN): $_" -Direction Inbound `
      -Action Allow -Program $_ -Protocol TCP -RemoteAddress LocalSubnet -Profile Any }
New-NetFirewallRule -DisplayName 'Разрешить порты 5000,5001 (LAN)' -Direction Inbound `
  -Action Allow -Protocol TCP -LocalPort 5000,5001 -RemoteAddress LocalSubnet -Profile Any
```

`-RemoteAddress LocalSubnet` означает «только устройства своей сети» — из интернета доступ
не открывается.

Автоматически то же самое делает инструмент:

```bash
python net_doctor.py --fix          # создаст netdoctor_fix.ps1
# затем запустить netdoctor_fix.ps1 от имени администратора (или --apply-fix)
```

Скрипт починки сам включает брандмауэр для всех профилей, переводит сеть в «частную»,
добавляет правило на порты и **отдельные правила для тех самых `python.exe`/`pythonw.exe`,
которые слушают порты** (важно, когда установлено несколько версий Python или сервер
запущен как `pythonw.exe`, а правило сделано для `python.exe` — для брандмауэра это
разные файлы).

Если после включения брандмауэра сервер снова пропал — запустите инструмент и посмотрите
раздел «Python-процессы и правила брандмауэра» и журнал блокировок: он покажет, какое
именно правило/профиль режет, и добавит подходящее.

## Ключи

```
--port N            порт тестового сервера (по умолчанию 8770)
--check-port N      проверить ваш сервер на порту N (кто слушает, на каком адресе)
--phone IP          IP телефона: проверка подсети, ping, ARP
--wait СЕК          сколько ждать запрос с телефона (по умолчанию 120)
--no-server         только проверки, без тестового сервера
--open              открыть страницу тестового сервера в браузере ноутбука
--fix               создать netdoctor_fix.ps1 и netdoctor_undo.ps1
--apply-fix         создать и сразу запустить (Windows спросит права UAC)
--program-rule      в fix-скрипт добавить разрешение для python.exe (только LAN)
--iface ИМЯ         какой интерфейс переводить в Private (по умолчанию — сам найдёт)
--report ФАЙЛ       куда сохранить отчёт (по умолчанию netdoctor_report.txt)
--no-qr             не печатать QR-код
--selftest          прогнать встроенные тесты (используется в CI)
```

## Что создаётся на диске

| Файл | Когда | Что это |
|---|---|---|
| `netdoctor_report.txt` | всегда | Полный отчёт: проверки, факты, адаптеры, адреса, слушающие порты, ARP, все запросы к тестовому серверу, вердикт. Можно переслать целиком. |
| `netdoctor_fix.ps1` | `--fix` / `--apply-fix` | Починка: профиль сети → Private, правило входящих TCP **только для локальной подсети** на нужные порты, сам запрашивает UAC. |
| `netdoctor_undo.ps1` | `--fix` / `--apply-fix` | Полный откат: удаляет все правила `netdoctor*`. |

> 🔒 **Безопасность.** Правила брандмауэра создаются только с `-RemoteAddress LocalSubnet` —
> это значит «доступ из своей сети» (телефон, планшет, другой ноутбук дома), и
> **не** открывает сервер в интернет. Профиль сети переводится в Private, обратно
> скрипт его не меняет — это может быть вредно.

## Коды возврата

`0` — проблем не найдено (или телефон достучался), `2` — найдены проблемы,
`1` — внутренняя ошибка инструмента, `130` — прервано (Ctrl+C).
Это удобно для скриптов: `python net_doctor.py --no-server || echo "есть проблемы"`.

## Новые порты, новые версии Python и «решить раз и навсегда»

Windows разрешает входящие **двумя разными способами**, и это ключ к пониманию проблемы:

| Тип правила | Что покрывает | Когда ломается |
|---|---|---|
| По программе (`-Program python.exe`) | указанный `.exe` на **любых портах**, только `LocalSubnet` | смена версии Python → другой файл → правило не действует |
| По порту (`-LocalPort 5000,5001`) | **любую** программу на этих портах | новый порт не покрыт |

Поэтому «навсегда» — это **правила по программам** для всех ваших интерпретаторов,
выданные на все порты, но только для своей локальной сети. Именно так делает `--fix`:

```powershell
# пересоздать правила (запускать от администратора или через --apply-fix)
python net_doctor.py --no-server --fix
```

`netdoctor_fix.ps1` теперь:
1. включает брандмауэр для всех профилей (если он был выключен — включит);
2. переводит сеть в «частную»;
3. добавляет правило на известные порты (8770, 5000, 8000, ваши `--extra-port`/`--check-port`);
4. добавляет правила **для каждого найденного `python.exe`/`pythonw.exe`** (и тех,
   что слушают порты сейчас, и всех установленных версий из `py -0p`) на **все TCP-порты**,
   только `RemoteAddress LocalSubnet`.

Что это даёт:
* новый сервер на **новом порту** тем же интерпретатором — заработает сразу, без правок;
* `python.exe` и `pythonw.exe` — **разные файлы** для брандмауэра; правила создаются на оба;
* поставили ещё одну версию Python — выполните `--fix` один раз, он подхватит её путь
  и добавит правила (автоматически узнаётся из `py -0p`).

**Из интернета ничего не открывается:** везде `RemoteAddress LocalSubnet` — доступ только
устройствам вашей сети. Откат — `netdoctor_undo.ps1` (удаляет все правила `netdoctor*`).

## Почему это ломается «само» (и при чём тут отпуск)

Три механизма, которые дают ровно вашу картину «на ноутбуке открывается, с телефона нет»:

1. **Правило сделано для другого файла.** Windows спрашивает «Разрешить доступ?» один раз —
   при первом запуске конкретного `.exe`. Если сервер запускается как `pythonw.exe`
   (без окна) или из нового интерпретатора, а правило есть только для `python.exe`
   старой версии, входящие молча блокируются — никаких сообщений не появляется.
2. **Появился новый путь к интерпретатору.** Обновление Python (в т.ч. через Microsoft Store)
   или установка второй версии создаёт новый файл в новом каталоге. Старые правила
   по-прежнему указывают на прежний путь и больше ничего не разрешают.
3. **Windows при обновлении пересоздал сетевой профиль или сбросил политику входящих**
   (сеть снова «Общедоступная» либо включён режим «блокировать все входящие»). Тогда
   перестают помогать даже корректные правила.
4. **Правила созданы для другого профиля сети.** У каждого правила брандмауэра есть
   профиль: `Private`, `Public`, `Domain` или `Any`. Windows применяет правило только
   тогда, когда активный профиль сети в него входит. Типичная (и очень коварная) картина:
   правила для `python.exe` создавались, когда сеть была «Общедоступной» → у них
   `Profile = Public`; после поездки Windows пересоздал/переопределил домашнюю сеть
   как «Частную» → **все эти правила молча перестали действовать**, хотя выглядят
   включёнными и указывают на правильный `python.exe`.

   Как выглядит в отчёте (реальный случай):

   ```
   Активные профили брандмауэра: Private
   {"Program": "...\pythoncore-3.14-64\pythonw.exe", "Profile": "Public", ...}
   ВНИМАНИЕ: правила ... созданы для профилей ['Public'], а активны ['Private'] — не применяются
   ```

   Лечение: `--fix` создаёт свои правила с `-Profile Any`, то есть они действуют
   на любой сети (и всё равно только `LocalSubnet`).

Проверить, какой именно случай был у вас, можно только по «до/после»: сохраните отчёт
(`netdoctor_report.txt`) когда всё работает — это база для сравнения. Инструмент в отчёте
печатает и пути слушающих процессов, и пути из правил, и состояние профилей.

## У других пользователей будет так же?

Условие «одна локальная сеть + выключенные VPN + настроенные антивирус и брандмауэр»
само по себе **не гарантирует** доступ: брандмауэру Windows всё равно нужно явное
разрешение для **того самого файла**, который слушает порт. Типичные ловушки одинаковы
у всех:

* разрешение выдано для `python.exe`, а сервер запущен `pythonw.exe`;
* новая версия Python = новый путь = старые правила не работают;
* сеть помечена как «Общедоступная» (ломается после поездок/новых сетей);
* правило ограничено чужой подсетью (например, хот-спота `192.168.137.0/24`);
* режим «блокировать все входящие» сведёт на нет любые разрешающие правила;
* сетевой экран антивируса (ESET, Kaspersky, Malwarebytes) фильтрует поверх Windows.

Поэтому «предугадать для всех» можно так: этот чек-лист + запуск инструмента в режиме
проверки и сохранение отчёта как эталона:

```bash
python net_doctor.py --no-server --check-port 5000 --report здоровый_отчёт.txt
```

А `--fix` избавляет от ручной возни: он создаёт правила разом для всех интерпретаторов
и всех нужных портов — только для своей сети.

## Частые вопросы

**Почему на самом ноутбуке по `192.168.0.60` открывается, а на телефоне — нет?**
Потому что трафик «сам с собой» не проходит через фильтр входящих подключений.
Это ровно та ситуация, для которой сделан инструмент: адрес и сервер в порядке,
а входящий доступ режется (брандмауэр, WARP/VPN, профиль сети, роутер).

**Может, сразу выключить брандмауэр?**
Можно на 1 минуту для проверки: `netsh advfirewall set allprofiles state off` →
тест → обязательно `netsh advfirewall set allprofiles state on`. Постоянно выключать
не стоит; правильное решение — одно узкое разрешающее правило (это и делает `--fix`).

**Я запускаю `.bat` и вижу «'on' is not recognized as an internal or external command» —
что делать?**

Это та самая поломка `.bat`, описанная выше. Обновите файлы из репозитория
(в актуальной версии `.bat` чистый ASCII без `chcp`, а основной запуск — `.vbs`)
и запускайте **`start_netdoctor.vbs`**. Если обновление невозможно — просто запустите
Python вручную в папке `netdiagn`:

```bat
python net_doctor.py
```

**А если у меня не 5000, а другой порт?**
Укажите его: `--check-port 8081`, а `--fix` создаёт правило на порт тестового сервера,
`--check-port` и стандартные 5000/8000. Дополнительный порт можно передать ключом
`--extra-port 8081` (можно несколько раз).
