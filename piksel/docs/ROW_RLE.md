# Разбор твоей идеи строкового RLE + доработка

> Идея: прозрачный фон не пишем, пишем только цветные куски построчно:
> `4: 3. #0f380f #306230 10x - #9bbc0f`
> где `4:` — строка, `3.` — столбец, `10x -` — 10 прозрачных, коды подряд.

---

## 1. Твоя идея — очень сильная

По сути ты изобрёл **sparse row-RLE** — то же что делает PICO-8 для хранения фона (`pico8rle` [lexaloffle.com/bbs/?tid=38884]) и GameBoy `png2gb` [github.com/basxto/gameboy-png-tools]: хранят только непустые строки и внутри строки — серии одинаковых тайлов.

Почему это лучше «пиксель x,y»:

- **Фон = 0 токенов.** Для персонажа 32×32 с полем 16×16 внутри (≈25% заполнения) ты экономишь ~75% текста. LLM не тратит силы на «прозрачный, прозрачный...».
- **Привязка к строке.** Номер строки `4:` — это якорь. LLM, которая пишет матрицы ASCII, часто «съезжает» — строка становится длиннее/короче. С явным `4:` ошибка видна сразу и парсер может её игнорировать/подсветить. Это как `line n` в Forth — LLM любит нумерацию.
- **RLE внутри строки.** `10x -` для 10 прозрачных подряд — это экономия ×10. Для сплошных заливок (плащ воина) `8x #b13e53` вместо 8 повторов.

**Оценка токенов** (пример: воин 32×32, ~300 цветных пикселей):
- Вариант A (пиксель x,y): 300 строк × ~6 токенов = ~1800 токенов
- Твоя идея (row-RLE с hex): ~18 строк × ~12 токенов = ~216 токенов — **в 8 раз меньше**
- С палитрой-индексами (см. ниже): ~18×8 = ~144 токена — **в 12 раз меньше**

Это критично: LLM-контекст ограничен, и чем короче сценарий — тем реже галлюцинации.

## 2. Что улучшить в твоём формате

Твоя запись `4: 3. #0f380f #306230 10x -` рабочая, но смешивает `:` и `.` и hex длинный. Предлагаю **v0.2 — совместимый, но короче**:

### Правило 1 — палитра индексами, а не hex

Hex `#0f380f` = 4 токена (`#`, `0f`, `38`, `0f`). Индекс `2` = 1 токен. Поэтому сначала объявляем палитру:

```
палитра gameboy: 0=#0f380f 1=#306230 2=#8bac0f 3=#9bbc0f
```

Дальше в строках пишем `0`, `1`, `2` вместо `#...`. Это как в PICO-8 (0–15) и Asset Forge — LLM уже видела такое.

### Правило 2 — прозрачный = `-`, но без `x` по умолчанию

Твой `-` для прозрачного — отлично. Оставляем. `10x -` = `10-` короче. Для цветных так же: `5x 2` = пять пикселей цвета 2.

### Правило 3 — явный разделитель строк

`4: 3. ...` можно упростить до `4 3: ...` — меньше типов знаков. Но оставим твой стиль, парсер поймёт оба.

### Итоговый синтаксис v0.2 (совместимый с твоим):

```
размер 32
палитра 0=#0f380f 1=#306230 2=#8bac0f 3=#9bbc0f
# затем только непустые строки:
4: 3. 0 1 10- 2
# читается: строка 4, столбец 3: цвет0, цвет1, 10 прозрачных, цвет2
# если подряд один цвет: 5: 0. 8x2  - значит 8 пикселей цвета 2 с колонки 0
# если строка полностью пустая — просто не пишем её
```

**Почему так нейросети удобно придумывать:**
- Она думает «рисую воина сверху вниз» — каждая строка = один шаг мышления, как в ASCII-арте (исследование SVE-ASCII показывает что LLM лучше генерирует построчно).
- Она видит палитру и может сказать «плащ — это 2, кожа — 3» и не повторять hex.
- Она может вначале написать грубый силуэт одними `0`, потом добавить детали `1` — это тот же «скетч → детализация» что ты хочешь для HD.

### Пример — воин с мечом (твой стиль, сжатый)

```
размер 32
палитра pico8: 0=#000 1=#fff 2=#ff004d 3=#ffccaa 4=#5d275d 5=#83769c 6=#3a1a0a
6: 12. 2x6
7: 11. 6 3 3 6
8: 10. 6 3 0 3 6
9: 9. 6 3 3 3 3 6
10: 8. 6 2 2 2 2 2 6
# меч: вертикаль
3: 22. 1 1
4: 22. 1 0 1
5: 22. 1 0 1
...
```

Полный файл уже в `piksel/examples/warrior.piksel` — скопируй в редактор и жми Собрать.

## 3. Твоя идея vs мои 3 варианта

| Критерий | Твоя row-RLE | A пиксель | B матрица | C области |
|---|---|---|---|---|
| Токены (воин 32×32) | **~150** | ~1800 | ~320 | ~80 (если заливка) |
| Читаемость | высокая | низкая | средняя | высокая |
| Правка 1 пикселя | легко (найти строку) | легко | тяжело (считать символы) | легко |
| LLM любит | **да** — построчно | нет | да | да |
| Поддержка фона | идеальна (не пишем) | идеальна | плохо (пишешь `...`) | идеальна |
| Сложные формы | средне | отлично | отлично | плохо (нужны примитивы) |

**Вывод:** твоя идея **лучше всех для спрайтов/персонажей** (sparse). Вариант C (`заливка/прямо`) лучше для фонов/тайлов (dense). Поэтому делаем **гибрид**: парсер понимает оба. LLM выбирает что короче.

Если LLM захочет нарисовать небо — напишет `заливка 0,0-31,11 3` (1 строка). Если воина — напишет 18 строк `4: 3. ...`. Это и есть «нейросеть сама выбирает уровень».

## 4. Что уже придумано кроме базового покраса

Ты спрашивал «что кроме заливки» — вот фишки из мира пиксель-арта, которые стоит поддержать командами:

- **Кластеры** — главный закон: не одиночные пиксели-шумы, а группы 2×2+. Научный стандарт [edukatesg.com — Gold Standard of Pixel Art]: «спроси какие 3 самых больших кластера — если не можешь ответить, переделывай массы». Команда `сгладить` может автоматически сливать одиночки.
- **Hue shifting** — тень не просто темнее, а холоднее (к синему), свет — теплее (к жёлтому). Практика из [pixel-editor.com]: «flat ramp vs hue-shifted — второй выглядит объёмнее теми же цветами». Команда `палитра тень=холод свет=тепло`.
- **Dithering** — шахматы `▒` для перехода. В PICO-8/GameBoy это база. Команда `дизеринг 5,10-15,15 1 2 шахматы`.
- **Outline** — селективный: тёмный контур только снаружи, внутри — цвет объекта. Команда `контур 1px #000 выборочно`.
- **Anti-aliasing ручной** — полутона на ступеньках. Команда `сгладить ступеньки 1px`.
- **Jaggies / Banding / Pillow shading** — три ошибки которые научные статьи выделяют как «убийцы читаемости» [purplepwny.com]. Автопроверка найдёт их.
- **Силуэт-тест** — заливаешь чёрным, смотришь узнаваем ли персонаж. Если нет — переделывай. Проверка `check силуэт контраст>30%`.
- **Палитра-ограничение** — не «магия 16», а «визуальная иерархия»: 4 цвета для GameBoy, 16 для PICO-8 достаточно. Пресеты `gameboy/pico8/nes/sweet16` уже в коде.
- **Tile reuse** — как в PICO-8 map: один тайл 8×8 повторяется. Команда `тайл 8x8 id=трава ...` + `карта 0,0 трава 1,0 трава`.

Всё это — по одной строке DSL, а не ручной труд.

## 5. Что нужно нейросети чтобы хорошо рисовать

- **Палитра заранее.** Дать `палитра gameboy` — и она не будет выдумывать 100 цветов. Это как дать `param height=95` в ФОРМЕ.
- **Обратная связь как в ФОРМЕ — нужна, но другая.** В ФОРМЕ `check watertight, check wall 3..5` — геометрия. Здесь:
  - `check палитра <=4` — не расползлась ли
  - `check кластер мин=4` — нет одиночек
  - `check силуэт` — узнаваем ли чёрный силуэт
  - `check контраст` — читается ли на фоне
  - Парсер сразу подсвечивает ошибки: «строка 4: столбец 33 вне размера» — как `error-bar` в ФОРМЕ.
  Эта обратная связь — **ключ**: исследование Asset Forge показало что LLM-judge с картинкой + ASCII сеткой оценивает лучше чем без неё [matthewdeaves.github.io/assetforge]. Значит надо показывать LLM скриншот после сборки, а не только текст.

- **Пример-шаблон в промпте.** Дать один готовый воин как few-shot — и LLM копирует формат. В ФОРМЕ это `docs/RECIPES.md`, здесь будет `examples/warrior.piksel`.

---

Научные данные: принципы выше — не вкусовщина, а консенсус из Gold Standard [edukatesg], Pixel VQ-VAE [exag.org] («каждый токен = группа пикселей»), и оценки LLM-judge [assetforge]. Всё сходится: **короткий sparse DSL + палитра + автопроверки = то что нужно чтобы нейросеть рисовала стабильно.**
